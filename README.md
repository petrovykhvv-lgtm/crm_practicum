# CRM-lite для агентства выставочных стендов

Локально запускаемая CRM-lite: интерфейс, серверная логика, база данных, конвертация лидов, воронка сделок, активности и дашборд.

> Статус: рамки проекта зафиксированы, локальный запуск подготовлен, модель данных и CRUD реализованы (фазы 0–2, часть 3–4). Реализация ведётся по шагам, см. [Plan.md](Plan.md).

## Легенда

Агентство проектирует и строит выставочные стенды, пространства и бренд-зоны. Запросы приходят с сайта, по почте, телефону, через рекомендации, а также менеджеры заводят их вручную.

Продажа редко закрывается сразу. Менеджер:

1. квалифицирует лид;
2. связывает его с компанией и контактным лицом клиента;
3. оценивает бюджет, уточняет площадку, сроки и формат работ;
4. ведёт сделку по стадиям до успешного закрытия или отказа.

Пользователи CRM — менеджеры. Им важно не терять входящие запросы, видеть воронку сделок, помнить контактных лиц клиента, отслеживать просроченные задачи и понимать объём потенциальной выручки в работе.

## Стек

Next.js, React, TypeScript, PostgreSQL, Prisma, Zod.
Строго зафиксированные версии: `prisma@6.19.3`, `@prisma/client@6.19.3`, `chart.js@4.5.1`, `react-chartjs-2@5.3.1`.
`DATABASE_URL` читается в `schema.prisma` через `env("DATABASE_URL")`. `@prisma/adapter-pg`, `PrismaPg` и `prisma.config.ts` не используются.

## Воспроизводимый локальный запуск

### Требования
- Node.js 20.9 или новее и npm.
- Docker с Docker Compose **или** уже установленный локальный PostgreSQL 14+ (см. вариант Б).

### Вариант А. PostgreSQL в Docker (по умолчанию)

```bash
npm install                # зависимости строго по package-lock.json, затем prisma generate
cp .env.example .env       # значения по умолчанию подходят для Docker
npm run db:up              # PostgreSQL 16 на localhost:5433, ждёт готовности
npm run db:deploy          # применяет миграции из prisma/migrations
npm run db:seed            # контрольные данные
npm run dev                # http://localhost:3000
```

Правок кода под окружение не требуется. Остановить базу: `npm run db:down` (данные сохраняются в томе Docker; `docker compose down -v` удалит и их).

### Вариант Б. Локальный PostgreSQL без Docker

1. Создайте роль и базу (пример для своей машины, пароль замените на свой):
   ```sql
   CREATE ROLE crm_practicum LOGIN PASSWORD 'ваш_пароль' CREATEDB;
   CREATE DATABASE crm_practicum OWNER crm_practicum;
   ```
   `CREATEDB` нужен Prisma для временной shadow-базы при `prisma migrate dev`.
2. Выполните `npm install` и `cp .env.example .env`.
3. В `.env` замените `DATABASE_URL` на свою строку подключения, например `postgresql://crm_practicum:ваш_пароль@localhost:5432/crm_practicum?schema=public`.
4. Дальше те же команды: `npm run db:deploy`, `npm run db:seed`, `npm run dev`.

### Переменные окружения
`.env.example` — шаблон, который лежит в репозитории. Файл `.env` с реальными значениями создаётся локально и находится в `.gitignore`, в репозиторий не попадает. Единственная переменная — `DATABASE_URL`, схема читает её через `env("DATABASE_URL")`. Пароль в `.env.example` — учебный, только для локальной базы.

### Seed и reset
- **Seed** (`prisma/seed.ts`) сначала очищает таблицы, затем создаёт предсказуемый набор с фиксированными id: 6 стадий воронки, 4 компании, 5 контактов, 6 лидов, 6 сделок и 8 активностей. Лиды покрывают все 5 источников и 5 статусов (`new` ×2, `in_progress`, `qualified`, `converted`, `disqualified`). По одной сделке на каждую стадию, включая `won` и `lost`. Активности: 2 заметки и 6 задач, из них 2 просрочены, 2 назначены на сегодня, 1 в будущем, 1 выполнена. В seed также создаётся история переходов по стадиям за последние 8 недель. Сделка `opp_2` создана «зависшей» (последнее изменение 20 дней назад) и имеет просроченную задачу, сделка `opp_4` тоже имеет просроченную задачу, поэтому блок «Сделки, требующие внимания» не пустой. Даты отсчитываются от начала текущего дня, поэтому «просрочено» и «сегодня» верны при любом запуске. В конце seed сверяет количества и завершается ошибкой при расхождении. Его можно запускать повторно, результат каждый раз одинаковый.
- **Reset** (`npm run db:reset`) удаляет **все** данные в базе из `DATABASE_URL` и пересоздаёт схему по миграциям, затем автоматически запускает seed. Используйте только с локальной dev-базой.
- Быстро вернуть демо-данные, не трогая схему: `npm run db:seed`.

### Как безопасно менять схему
1. Меняйте только `prisma/schema.prisma`, руками SQL в существующих миграциях не правьте.
2. Выполните `npm run db:migrate -- --name краткое_описание`. Prisma создаст новую папку в `prisma/migrations/` и применит её.
3. Просмотрите сгенерированный `migration.sql`. Если он удаляет или переименовывает колонку, Prisma предупредит о потере данных. Для переименования сначала сделайте миграцию с `--create-only` и исправьте SQL вручную.
4. Если менялись поля, которые использует seed, обновите `prisma/seed.ts` и выполните `npm run db:seed`.
5. Закоммитьте `schema.prisma` вместе с новой папкой миграции.
6. Товарищи по команде после `git pull` выполняют `npm install` и `npm run db:deploy`.

Никогда не выполняйте `db:reset` и `prisma migrate dev` на базе с реальными данными.

### Если что-то пошло не так
- `Can't reach database server`: база не запущена или порт не тот. Проверьте `npm run db:up` и порт в `DATABASE_URL` (5433 для Docker, 5432 для локальной установки).
- Порт 5433 занят: поменяйте левую часть в `ports` в `docker-compose.yml` и порт в `.env`.
- Ошибка `@prisma/client did not initialize yet`: выполните `npm run db:generate`.
- База «разошлась» со схемой после смены ветки: `npm run db:reset`.

## Обязательные сущности

| Сущность | Назначение |
|---|---|
| `Lead` | Входящий запрос. Обязательный `source`: `site`, `email`, `phone`, `referral`, `manual`. Содержит бюджет, площадку, сроки и формат работ. |
| `Account` | Компания-клиент. |
| `Contact` | Контактное лицо, принадлежит `Account`. |
| `Opportunity` | Сделка: компания, контакт, стадия, сумма, статус `open`, `won` или `lost`. |
| `Stage` | Стадия воронки с порядком и признаком закрытия. Хранится в БД. |
| `StageTransition` | История попаданий сделки на стадии (стадия, сумма на момент перехода, дата). Заполняется автоматически при создании сделки, смене стадии и конвертации лида, из неё строится динамика на дашборде. |
| `Activity` | Заметка (`note`) или задача (`task`) со сроком `dueDate` и признаком `done`. Привязывается к сделке, лиду, контакту или компании. |

Связи: `Account 1—N Contact`, `Account 1—N Opportunity`, `Contact 1—N Opportunity`, `Stage 1—N Opportunity`, `Lead 0..1—1 Opportunity` (после конвертации), `Activity N—1` к сделке, лиду, контакту или компании.

## Статусы лидов

| Код | Название | Смысл |
|---|---|---|
| `new` | Новый | Только поступил, не взят в работу. |
| `in_progress` | В работе | Менеджер связался, уточняет детали. |
| `qualified` | Квалифицирован | Есть потребность, бюджет и сроки, готов к конвертации. |
| `converted` | Конвертирован | Создан контакт и компания, при необходимости сделка. Финальный статус. |
| `disqualified` | Отклонён | Не подходит или неактуален. Указывается причина. |

Переходы: `new → in_progress → qualified → converted`. Из `new`, `in_progress` и `qualified` можно перейти в `disqualified`. Из `disqualified` можно вернуть в `in_progress`. Из `converted` выхода нет.

## Стадии воронки сделок

| Порядок | Код | Название | Тип |
|---|---|---|---|
| 1 | `new` | Новая | открытая |
| 2 | `qualification` | Квалификация (площадка, сроки, бюджет) | открытая |
| 3 | `proposal` | Смета / КП | открытая |
| 4 | `negotiation` | Согласование | открытая |
| 5 | `won` | Выиграна | закрытая |
| 6 | `lost` | Проиграна | закрытая |

Правила статусов сделки:
- Пока стадия открытая, статус `open`.
- Переход на `won` требует сумму больше 0, компанию и контакт. Статус становится `won`, фиксируется `closedAt`.
- Переход на `lost` требует причины отказа (`lostReason`). Статус становится `lost`, фиксируется `closedAt`.
- Закрытую сделку можно вернуть на открытую стадию. Тогда статус `open`, а `closedAt` и `lostReason` очищаются.
- Переход между открытыми стадиями допустим в любом направлении.

## Конвертация лида (`convert lead`)

Запуск: кнопка «Конвертировать» в блоке «Конвертация» карточки лида открывает страницу `/leads/{id}/convert`. Доступна для лидов в статусах `new`, `in_progress`, `qualified`.

Форма предзаполняется данными лида и состоит из трёх частей:
1. **Контакт:** имя и фамилия (обязательны), должность, email, телефон. Имя лида делится на «имя» и «фамилию» по первому пробелу, если фамилии нет, её нужно ввести.
2. **Компания:** выбор существующей или «+ Создать новую компанию» (тогда обязательно название). Если в базе есть компания с таким названием (без учёта регистра), она выбирается автоматически, дубликат не создаётся.
3. **Сделка (по желанию):** флажок «Создать сделку на стадии «Новая»». Название обязательно, сумма берётся из бюджета лида, площадка и дата из данных лида.

Конвертация выполняется одной транзакцией: создаются контакт, при необходимости компания и сделка, лид получает статус `converted`, `convertedAt` и ссылки на созданные записи (`convertedAccountId`, `convertedContactId`, у сделки `leadId`). Если что-то не удалось, не сохраняется ничего.

Защита: повторная конвертация запрещена (проверяется атомарно на сервере, даже если форма была открыта раньше), отклонённого лида конвертировать нельзя, без обязательных данных конвертация не выполняется. После успеха в карточке лида показываются ссылки на компанию, контакт и сделку, а в карточках компании, контакта и сделки виден «Исходный лид».

## MVP

Входит:
- CRUD, списки и карточки лидов, компаний, контактов и сделок;
- связи между сущностями и переходы по ним из карточек;
- поиск и фильтры (по статусу, источнику, стадии, компании, сроку задач);
- конвертация лида;
- воронка сделок по стадиям и смена стадии;
- заметки и задачи, отметка выполнения;
- быстрые действия;
- дашборд;
- `.env.example`, PostgreSQL в Docker, схема Prisma, `seed` и `reset`, `README.md`.

Не входит: авторизация и роли, интеграции с почтой и телефонией, вложения, отчёты на экспорт, уведомления.

## Быстрые действия

1. Создать сделку.
2. Сменить стадию сделки.
3. Добавить заметку (`note`).
4. Добавить задачу (`task`) со сроком.
5. Конвертировать лида (`convert lead`).

## Метрики дашборда

Все показатели считаются запросом к БД при каждом открытии дашборда.

| Метрика | Расчёт |
|---|---|
| Новые лиды | Количество лидов за последние 30 дней |
| Лиды по статусам | Количество лидов на каждый статус |
| Лиды по источникам | Количество лидов на каждый `source` (диаграмма) |
| Конверсия лидов | `converted / все лиды`, в процентах |
| Сделки в работе | Количество сделок со статусом `open` |
| Выручка в работе | Сумма сделок со статусом `open` |
| Воронка по стадиям | Количество и сумма открытых сделок на стадию (диаграмма) |
| Выиграно за месяц | Сумма и количество сделок `won` за текущий месяц |
| Доля выигранных (win rate) | `won / (won + lost)` за всё время, в процентах |
| Просроченные задачи | `task` с `done = false` и `dueDate` раньше сегодняшней даты |
| Задачи на сегодня | `task` с `done = false` и `dueDate` сегодня |

## Интерфейс и CRUD

Разделы: Лиды `/leads`, Воронка `/pipeline`, Задачи `/tasks`, Компании `/accounts`, Контакты `/contacts`, Сделки `/opportunities`. Для каждого доступны список, карточка со связанными записями, создание, редактирование и удаление. Дашборд открывается на главной странице `/`.

**Валидация.** Все правила описаны Zod-схемами в `src/lib/validation.ts` и выполняются на сервере в Server Actions (`src/lib/actions/`). В формах дополнительно стоят HTML-атрибуты (`required`, `type="email"`, `maxLength`) для мгновенной подсказки. Ошибки по полям показываются под полем, ошибки бэкенда (нет связи с базой, запрет удаления, нарушение правил) выводятся сообщением над формой или рядом с кнопкой «Удалить». Введённые значения при ошибке не теряются.

**Правила данных:**
- Лид: обязательны имя и источник; при статусе «Отклонён» нужна причина отказа; статус «Конвертирован» вручную не выставляется.
- Компания: обязательно название. Контакт: имя, фамилия и компания.
- Сделка: обязательны название, компания и стадия; контакт должен принадлежать выбранной компании. Статус выводится из стадии: `Выиграна` требует сумму больше 0 и контакт, `Проиграна` требует причину отказа, любая открытая стадия ставит статус `open` и очищает дату закрытия.

**Правила удаления:**
- Лид: нельзя удалить конвертированного. Активности лида удаляются вместе с ним.
- Компанию нельзя удалить, пока есть контакты, сделки или конвертированные лиды.
- Контакт нельзя удалить, пока он связан со сделками или конвертированными лидами. Сменить компанию у контакта со сделками тоже нельзя.
- Сделка удаляется вместе со своими активностями.

## Связи, поиск и фильтры

**Связи в карточках:**
- Лид: данные, блок «Конвертация» (что будет создано, найдена ли компания с таким названием, недоступна ли конвертация), после конвертации ссылки на компанию, контакт и сделку, активности.
- Компания: контакты, сделки со стадией и суммой, активности.
- Контакт: компания, сделки, активности.
- Сделка: компания, контакт, стадия и статус, исходный лид, активности.

**Поиск** без учёта регистра. Запрос из нескольких слов работает как «и»: `иван орлов` найдёт контакт «Орлов Иван».
- Глобальный поиск: поле в левом меню, страница `/search` (контакты, компании, сделки, лиды).
- Лиды: имя, компания, email, телефон. Компании: название, город, отрасль. Контакты: имя, фамилия, компания, email, должность. Сделки: название, компания, имя контакта.

**Фильтры** (значения в адресной строке, поэтому ссылкой на результат можно поделиться):
- Лиды: источник `?source=site` и статус `?status=new`.
- Сделки: стадия `?stage=proposal` и статус `?status=open|won|lost`.
- Поиск и фильтры сочетаются, кнопка «Сбросить» очищает их. Неизвестные значения игнорируются.

Все запросы выполняются к базе при каждом открытии страницы.

## Воронка, быстрые действия и активности

**Воронка** `/pipeline`: колонки по стадиям с количеством и суммой сделок, карточки сделок со ссылкой на карточку. Карточки можно **перетаскивать мышью** между колонками (HTML5 Drag and Drop, без внешних библиотек): колонка-цель подсвечивается, карточка перемещается сразу, а результат подтверждает сервер. Если правила не выполняются (нет суммы или контакта для «Выиграна»), карточка возвращается на место и показывается сообщение. При переносе в «Проиграна» открывается окно для ввода причины отказа. Перенос пишется в историю стадий. На тач-экранах и для клавиатуры остаётся выбор стадии в списке внутри карточки (нативный drag на тач-устройствах не работает). Стадия в воронке и в карточке сделки читается из одного поля базы, поэтому всегда совпадает.

**Быстрые действия:**
- Создать сделку: на странице воронки, форма из трёх полей (название, компания, сумма). Сделка создаётся на первой стадии.
- Сменить стадию: селект в карточке сделки и в карточке воронки, кнопка «Перевести». Для «Проиграна» появляется поле причины отказа.
- Добавить заметку и добавить задачу: форма в блоке «Активности» карточки лида, компании, контакта и сделки.
- Конвертировать лида: кнопка в карточке лида.

**Правила перевода** (одни и те же для смены стадии и для формы редактирования сделки):
- `won` заблокирован, если не указана сумма больше 0 или не привязан контакт;
- `lost` заблокирован, если не указана причина отказа;
- возврат на открытую стадию очищает причину отказа и дату закрытия. Сообщение о блокировке показывается на месте действия.

**Активности:** заметка (`note`) с текстом, задача (`task`) с обязательным сроком `dueDate` и признаком `done`. Задача отмечается флажком слева, при отметке сохраняется `completedAt`. Невыполненные задачи в ленте идут первыми по сроку, просроченные подсвечены, сегодняшние помечены. Срок сохраняется как полдень выбранной даты в часовом поясе сервера, поэтому «сегодня» и «просрочено» считаются от начала дня сервера.

## Дашборд

Страница `/` (пункт «Дашборд» в шапке). Все числа считаются на сервере при каждом открытии страницы запросами Prisma `groupBy`, `aggregate` и `count` (`src/lib/dashboard.ts`). Кэша и технологий реального времени нет: чтобы увидеть изменения после правки лида или сделки, достаточно открыть или обновить страницу (в шапке дашборда указано время получения данных).

- **Период и шаг динамики** (панель над KPI): пресеты 7 дней, 30 дней, 90 дней, 6 месяцев, год (по умолчанию 90 дней) или свои даты «с» и «по» (если указаны обе, они важнее пресета, максимум 731 день). Шаг графиков: авто, по дням, по неделям, по месяцам. Авто выбирает шаг по длине периода (до 31 дня по дням, до 180 по неделям, дальше по месяцам). Если точек больше 120, шаг укрупняется сам. Выбор хранится в адресной строке (`/?period=30d&step=day`, `/?from=2026-08-01&to=2026-09-30&step=month`), некорректные значения игнорируются. Разбор параметров в `src/lib/period.ts`, границы считаются в UTC, как и группировка `date_trunc` в БД.
- **Что зависит от периода:** графики динамики по этапам, «Всего лидов: за период», «Конверсия лидов» (доля конвертированных среди лидов, созданных за период), «Выиграно за период» и win rate (по сделкам, закрытым за период). Воронка, списки и остальные KPI показывают текущее состояние.
- **KPI:** всего лидов, открытых сделок, сумма открытых сделок, просроченные задачи. Дополнительно: конверсия лидов, выиграно за период, доля выигранных, лиды за период, задачи на сегодня.
- **Воронка продаж** (Chart.js): центрированные столбцы по этапам с объёмом денег и числом сделок. Объём этапа — сумма сделок, дошедших до него и дальше, поэтому воронка сужается. Проигранные сделки в воронку не входят, отказы выводятся отдельным числом на самом графике (плашка «Отказы»).
- **Динамика объёма по этапам:** линейные графики за выбранный период с выбранным шагом (день, неделя или месяц), по каждому этапу воронки показано, сколько денег попало на этап за шаг. Данные берутся из `StageTransition` (группировка по неделе на стороне PostgreSQL). Значения на точках в млн ₽, в подсказке точная сумма.
- **Диаграммы Chart.js** (`chart.js@4.5.1`, `react-chartjs-2@5.3.1`): воронка и графики динамики. Клиентский компонент `src/components/dashboard-charts.tsx` получает от сервера только подготовленные массивы подписей, чисел и цветов через props.
- **Сводки:** по статусам лидов и по источникам (`site`, `email`, `phone`, `referral`, `manual`) с количеством и долей.
- **Сводки и списки в одну строку** (четыре блока рядом): сводка по статусам лидов, сводка по источникам, «Новые лиды», «Сделки, требующие внимания».
- Четыре блока ряда имеют одинаковую высоту, длинное содержимое прокручивается внутри блока. Везде показаны суммы: в сводках по статусам и источникам суммарный бюджет лидов (`aggregate _sum` по полю `budget`), у каждого лида в «Новых лидах» его бюджет, у каждой сделки в «Сделках, требующих внимания» сумма сделки.
- **Новые лиды:** 20 последних лидов. **Сделки, требующие внимания:** открытые сделки, у которых есть просроченная задача или которые не менялись дольше `STUCK_DAYS` (14 дней, константа в `src/lib/dashboard.ts`). У каждой указана причина (просроченные задачи со сроком и/или число дней без изменений). Список отсортирован по убыванию суммы сделки (сделки без суммы в конце), показываются до 50 сделок. Просроченные задачи, привязанные к лидам, контактам и компаниям, учитываются в KPI «Просроченных задач», но в этот список не попадают.

## Задачи, правка активностей и подтверждения

- **Страница «Задачи»** `/tasks`: все задачи по сделкам, лидам, контактам и компаниям одним списком. Вкладки с счётчиками: Невыполненные (по умолчанию), Просрочено, Сегодня, Предстоящие, Выполненные, Все; поиск по тексту; у каждой задачи ссылка на сущность. Невыполненные идут по сроку, просроченные подсвечены. В меню у пункта «Задачи» красный счётчик просроченных, KPI «Просроченных задач» на дашборде ведёт на вкладку «Просрочено».
- **Правка и удаление активностей:** у каждой заметки и задачи в карточках и на странице «Задачи» есть «Изменить» (текст, для задачи и срок) и «Удалить». Тип активности не меняется, для задачи срок обязателен.
- **Подтверждение удаления:** собственное окно вместо системного `confirm`. В нём указаны последствия удаления, фокус стоит на «Отмена», `Esc` и клик по фону отменяют. Если бэкенд отказывает (например, у компании есть контакты), причина показывается внутри окна, оно остаётся открытым.
- **Ошибки в формах:** над формой выводится список ошибок, клик по пункту переводит фокус на поле. После неудачной отправки фокус сам переходит на первое поле с ошибкой, текст ошибки связан с полем через `aria-describedby`.

## Основной сценарий

1. Запуск проекта.
2. Подготовка демонстрационных данных.
3. Создание лида.
4. Конвертация лида в контакт и компанию, при необходимости в сделку.
5. Проверка связей в карточках.
6. Перевод сделки по стадиям.
7. Добавление заметки и задачи.
8. Проверка поиска и фильтров.
9. Открытие дашборда.
10. Изменение лида или сделки и повторная проверка дашборда.
