# CRM-lite для агентства выставочных стендов

Локально запускаемая CRM-lite на Next.js, React, TypeScript, PostgreSQL, Prisma и Zod: лиды, компании, контакты, сделки, воронка с перетаскиванием, активности (заметки и задачи), конвертация лидов, ответственные менеджеры, журнал изменений, импорт и экспорт CSV, дашборд с графиками Chart.js.

Что делает продукт, статусы, стадии, метрики дашборда: [docs/product.md](docs/product.md).

## Быстрый старт

```bash
npm install
cp .env.example .env     # значения по умолчанию подходят для Docker
npm run db:up            # PostgreSQL 16 в Docker на localhost:5433
npm run db:deploy        # применить миграции
npm run db:seed          # контрольные данные
npm run dev              # http://localhost:3000
```

Без Docker: см. [вариант Б](#вариант-б-локальный-postgresql-без-docker).

## Требования и окружение

- Node.js 20.9 или новее и npm.
- Docker с Docker Compose **или** локальный PostgreSQL 14+.
- Версии ключевых пакетов зафиксированы без `^`: `prisma@6.19.3`, `@prisma/client@6.19.3`, `chart.js@4.5.1`, `react-chartjs-2@5.3.1`. `DATABASE_URL` читается в `schema.prisma` через `env("DATABASE_URL")`. `@prisma/adapter-pg`, `PrismaPg` и `prisma.config.ts` не используются.

### Переменные окружения

`.env.example` лежит в репозитории, настоящий `.env` создаётся локально и в git не попадает (`.gitignore`). Пароль в примере учебный, только для локальной базы.

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к рабочей базе (обязательна). |
| `APP_TIMEZONE` | Часовой пояс для границ «сегодня», недель и месяцев (например, `Europe/Moscow`). Не задана: пояс сервера. |
| `DATABASE_URL_TEST` | Необязательно: тестовая база для `npm test`. Имя обязано оканчиваться на `_test`. |

## Запуск подробно

### Вариант А. PostgreSQL в Docker (по умолчанию)

```bash
npm install                # зависимости строго по package-lock.json, затем prisma generate
cp .env.example .env
npm run db:up              # контейнер crm-practicum-db, порт 5433, ждёт готовности
npm run db:deploy          # prisma migrate deploy: применяет prisma/migrations
npm run db:seed
npm run dev
```

Остановить базу: `npm run db:down` (данные сохраняются в томе; `docker compose down -v` удалит и их).

### Вариант Б. Локальный PostgreSQL без Docker

1. Создайте роль и базу (пароль замените на свой):
   ```sql
   CREATE ROLE crm_practicum LOGIN PASSWORD 'ваш_пароль' CREATEDB;
   CREATE DATABASE crm_practicum OWNER crm_practicum;
   ```
   `CREATEDB` нужен Prisma для временной shadow-базы в `prisma migrate dev` и тестам для создания `crm_practicum_test`.
2. `npm install` и `cp .env.example .env`.
3. В `.env` укажите свой `DATABASE_URL`, например `postgresql://crm_practicum:ваш_пароль@localhost:5432/crm_practicum?schema=public`.
4. Дальше те же команды: `npm run db:deploy`, `npm run db:seed`, `npm run dev`.

### Production-режим

```bash
npm run build
npm start                  # http://localhost:3000
```

## Seed и reset

**Seed** (`prisma/seed.ts`) сначала очищает таблицы данных, затем создаёт предсказуемый набор с фиксированными id. В начале он печатает, в какую базу пишет. В конце сверяет количества и завершается ошибкой при расхождении. Его можно запускать повторно, результат каждый раз одинаковый.

| Что | Сколько | Состав |
|---|---|---|
| Менеджеры | 3 | Анна Мельникова, Борис Кузнецов, Вера Соколова |
| Причины отказа | 6 | справочник, «Другое» требует комментарий |
| Стадии воронки | 6 | Новая, Квалификация, Смета / КП, Согласование, Выиграна, Проиграна (вероятности 10, 25, 50, 75, 100, 0 %) |
| Компании | 4 | «Экспо Плюс», Nordic Home, Fresh Lab, «Техно-М» |
| Контакты | 5 | у «Экспо Плюс» два |
| Лиды | 6 | все 5 источников, статусы: новый ×2, в работе, квалифицирован, отклонён, конвертирован |
| Сделки | 6 | по одной на каждую стадию; выигранная связана с конвертированным лидом, проигранная имеет причину |
| Активности | 8 | 2 заметки, 6 задач: 2 просрочены, 2 на сегодня, 1 в будущем, 1 выполнена |
| История стадий | 18 | за последние 8 недель, из неё строятся графики динамики |

Сделка `opp_2` «зависшая» (последнее изменение 20 дней назад) и вместе с `opp_4` имеет просроченную задачу, поэтому блок «Сделки, требующие внимания» на дашборде не пустой. Даты считаются от начала сегодняшнего дня в `APP_TIMEZONE`, поэтому «просрочено» и «сегодня» верны при любом запуске.

**Reset** (`npm run db:reset`) удаляет **все** данные в базе из `DATABASE_URL`, пересоздаёт схему по миграциям и автоматически запускает seed. Используйте только с локальной dev-базой. Prisma может потребовать явного согласия на выполнение reset (защитный механизм CLI), в обычном терминале этого нет.

> **Осторожно:** `seed` и `reset` стирают данные в базе из `DATABASE_URL`. Если нужно проверить что-то на чистых данных, создайте отдельную базу и задайте для команды явный URL: `DATABASE_URL="postgresql://…/crm_practicum_demo" npm run db:seed`. Имя базы печатается первой строкой вывода seed.

Быстро вернуть демо-данные, не трогая схему: `npm run db:seed`.

## Как безопасно менять схему

1. Меняйте только `prisma/schema.prisma`. SQL в уже применённых миграциях не правьте.
2. Перед изменением сделайте копию данных, если они вам нужны: `pg_dump -Fc crm_practicum > backup.dump`.
3. `npm run db:migrate -- --name краткое_описание`: Prisma создаст папку в `prisma/migrations/` и применит её. Для переименований и переноса данных используйте `--create-only`, поправьте `migration.sql` (например, добавьте `UPDATE`/`INSERT` для переноса) и примените `npm run db:deploy`. Так сделаны миграции `stage_transitions` и `team_forecast_reasons_audit` (они переносят существующие данные).
4. Просмотрите `migration.sql`: при удалении или переименовании колонки Prisma предупредит о потере данных.
5. Обновите `prisma/seed.ts`, если менялись поля, и `tests/` (интеграционные тесты применят все миграции к чистой тестовой базе и покажут несовместимость).
6. Закоммитьте `schema.prisma` вместе с новой папкой миграции.
7. Коллеги после `git pull` выполняют `npm install` и `npm run db:deploy`. После `prisma generate` перезапустите dev-сервер (клиент Prisma кэшируется).

Никогда не выполняйте `db:reset` и `prisma migrate dev` на базе с реальными данными.

## Тесты и CI

```bash
npm test
```

- Юнит-тесты: правила стадий, схемы Zod, периоды и часовые пояса, CSV, diff журнала.
- Интеграционные тесты на реальной PostgreSQL: действия создания, правки и удаления, конвертация лида (включая откат и гонку двух запросов), активности, воронка, импорт и экспорт, настройки, запросы списков, дашборд, seed и сквозной демонстрационный сценарий.
- **Тесты работают только на отдельной базе** `<имя рабочей базы>_test` (или `DATABASE_URL_TEST`). Имя обязано оканчиваться на `_test`, иначе тесты не стартуют, а `DATABASE_URL` внутри тестов принудительно подменяется. База создаётся и мигрируется автоматически (при необходимости создайте её вручную: `createdb crm_practicum_test`). Рабочие данные не затрагиваются.
- CI (`.github/workflows/ci.yml`): `prisma validate`, lint, typecheck, `npm test`, `build` на PostgreSQL 16.

## Ручная проверка работоспособности

После `npm run db:seed` и `npm run dev` пройдите чек-лист (около 10 минут). Подробные шаги и ожидаемые значения: [docs/demo-scenario.md](docs/demo-scenario.md).

- [ ] Дашборд `/` открывается: 6 лидов, 4 открытые сделки, просроченных задач 2, воронка и 5 линейных графиков отрисованы.
- [ ] «Лиды»: поиск, фильтры по источнику и статусу, сортировка по заголовкам, экспорт CSV открывается в Excel.
- [ ] Создание лида: пустое имя и некорректный email дают ошибки у полей, лид с email существующего даёт предупреждение о дублях.
- [ ] Конвертация лида создаёт компанию, контакт и сделку со ссылками; повторная конвертация запрещена.
- [ ] Воронка: перетаскивание карточки меняет стадию (то же в карточке сделки), «Отменить» возвращает, «Выиграна» без суммы или контакта блокируется, «Проиграна» просит причину.
- [ ] Заметка и задача со сроком добавляются, задача отмечается выполненной, правится и удаляется; «Задачи» показывает просроченные.
- [ ] Дашборд после изменений обновился при повторном открытии; выбор периода, шага и менеджера работает.
- [ ] «Настройки»: менеджеры, причины отказа, вероятности стадий сохраняются.

## Демонстрационный сценарий

`запуск → seed/reset/интерфейс → лид → convert lead → сделка → активность → воронка сделок → dashboard`. Сценарий подробно описан в [docs/demo-scenario.md](docs/demo-scenario.md) и автоматически проверяется тестом `tests/integration/scenario.test.ts`.

## Известные ограничения

- **Нет авторизации и ролей.** «Работаю как» в шапке выбирает менеджера для значений по умолчанию и фильтров, это не защита. Приложение рассчитано на локальный запуск и доверенных пользователей.
- Одна валюта (рубли), суммы без копеек в интерфейсе.
- Перетаскивание карточек работает мышью. На тач-экранах используйте «Сменить стадию» в карточке (нативный drag-and-drop на touch не поддерживается браузерами).
- Нет уведомлений и напоминаний (почта, push), нет вложений и пользовательских полей.
- Импорт только для лидов (экспорт для лидов, сделок, компаний и контактов), максимум 2000 строк и 2 МБ.
- История стадий для сделок, созданных до миграции `stage_transitions`, содержит одну запись на текущую стадию (прежняя история не хранилась), поэтому графики динамики по старым данным точны только с момента миграции.
- Журнал изменений охватывает действия через интерфейс; правки напрямую в базе в него не попадают.
- Полнотекстового поиска нет: `ILIKE` по основным полям (на больших объёмах потребуются индексы `pg_trgm`).
